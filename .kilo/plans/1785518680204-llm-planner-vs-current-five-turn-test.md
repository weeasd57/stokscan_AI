# خطة اختبار LLM Planner مقابل الوضع الحالي

## الهدف

إنشاء اختبار خارجي مؤقت لا يغيّر بنية الشات بوت أو منطق الإنتاج، ويقارن نفس تسلسل الأسئلة داخل جلستين مستقلتين:

1. وضع LLM Planner أولاً: استدعاء `runPlanner()` مباشرة واعتماد `intent` و`entities` و`tools` التي يرجعها الموديل، ثم تنفيذ الأدوات وبناء الرد من نفس النتائج دون تشغيل `buildCompoundDeterministicPlan()` أو `enforceIntentFromMessage()`.
2. الوضع الحالي: استدعاء `runPipeline()` كما هو حالياً، بما يشمل الـdeterministic planner والـintent enforcement والـtools والـfinal response الحالي.

لا يتم تعديل ملفات الإنتاج أو تغيير سلوك endpoint الشات.

## تسلسل الرسائل

تُرسل الرسائل الخمس بنفس الترتيب في كل وضع:

1. `جدوى أخباره إيه؟`
2. `تحليل السيولة لـ GDWA`
3. `إيه السهم أو القطاع المتوقع يرتفع الأسبوع ده؟`
4. `أفضل الفرص المتاحة حالياً`
5. `معايا سيولة ادخل في اي دلوقتي غير قطاع الادوية والمخابز علشان فيهم وطلعو الحمدالله خلاص`

كل وضع يستخدم `session_id` و`user_id` تجريبيين منفصلين، مع تمرير `state`, `summary`, و`history` من الرسالة السابقة داخل الوضع نفسه فقط. لا يتم استخدام بيانات جلسة موجودة مسبقاً.

## مكان الاختبار

إضافة Harness مستقل تحت `web/scripts/` أو تشغيله من ملف اختبار مؤقت غير مستورد من التطبيق. لا يتم تعديل `pipeline.ts`, `planner.ts`, `tools-v2.ts`, `final-v2.ts` أو routes.

يفضل أن يكون التشغيل بأمر مستقل مثل:

```text
npm --prefix web run test:planner-compare
```

ويُضاف script للاختبار فقط إذا كان ذلك ضرورياً، مع إبقاء التعديل خارج منطق التطبيق. إذا كان إنشاء script سيؤثر على ملفات المشروع أكثر من اللازم، يُشغّل الـHarness مباشرة بأداة التنفيذ الحالية.

## مسار وضع LLM Planner أولاً

لكل رسالة:

1. تسجيل وقت بداية الرسالة.
2. استدعاء `runPlanner(message, [], sessionState, history, apiKeys, null)` مباشرة.
3. تطبيع نتيجة الـLLM إلى شكل `PlannerResult` المطلوب من `executeStructuredTools`، مع الحفاظ على القيم التي رجعها الموديل وعدم فرض نية أو أدوات من القواعد deterministic.
4. اشتقاق احتياجات live/history بأقل تطبيع شكلي لازم لتشغيل الأدوات، دون تغيير `intent`, `entities.symbols`, أو `tools` التي اختارها الـLLM.
5. تنفيذ `executeStructuredTools()` بالـplan الناتج ورسالة المستخدم نفسها.
6. بناء الجداول من النتائج فقط عبر `buildExcelTables()` إن كان المسار الحالي يحتاجها.
7. بناء الرد النهائي من النتائج المهيكلة باستخدام `buildDeterministicResponse()` إن كان ذلك ممكناً؛ وإذا لم ينتج رداً، تسجيل أن وضع Planner-only لم يجد deterministic finalizer بدلاً من تحويل الاختبار إلى الوضع الحالي.
8. تسجيل زمن كل مرحلة والزمن الكلي.
9. تحديث `state`, `summary`, و`history` بناءً على ناتج هذه الرسالة فقط لاستمرار سياق الجلسة.

لا يُستدعى في هذا الوضع `buildCompoundDeterministicPlan()` أو `enforceIntentFromMessage()` أو `sanitizePlannerTools()`؛ هذه هي نقطة المقارنة الأساسية.

## مسار الوضع الحالي

لكل رسالة:

1. تسجيل وقت البداية.
2. استدعاء `runPipeline()` الحالي كما هو.
3. تسجيل `result.plan`, `result.response`, `result.session_update`، والزمن الكلي.
4. تحديث `state`, `summary`, و`history` بنفس طريقة الجلسة الحالية.

لا يتم تعديل استدعاء `runPipeline()` ولا تمرير flags جديدة له.

## التقرير المطلوب

يُحفظ تقرير JSON ونسخة Markdown/console، مع سجل مستقل لكل رسالة في كل وضع يحتوي على:

- رقم الدور ونص السؤال.
- الوضع: `llm_planner_first` أو `current_pipeline`.
- `intent` النهائي.
- الرموز المستخرجة.
- القطاع والزمن والفلاتر إن وجدت.
- الأدوات التي اختارها الـLLM أو الوضع الحالي.
- الأدوات التي نُفذت فعلياً.
- زمن استدعاء الـplanner.
- زمن تنفيذ الأدوات.
- زمن بناء الرد النهائي.
- الزمن الكلي بالملي ثانية.
- عدد نتائج كل Tool.
- تواريخ البيانات `data_time` و`data_type`.
- الرموز الموجودة داخل كل نتيجة Tool.
- الرد الكامل، بدون قصّه في JSON.
- الأخطاء والتحذيرات وسبب فشل أي مرحلة.
- `current_symbol` و`last_symbols` قبل وبعد كل رسالة.

يحتوي ملخص Markdown على جدول مقارنة لكل دور:

```text
الدور | السؤال | نية LLM | نية الحالي | أدوات LLM | أدوات الحالي | زمن LLM | زمن الحالي | فرق الزمن
```

ثم قسم منفصل لتعارضات grounding:

- رمز مطلوب ولم يظهر في النتائج.
- رمز ظهر في النتائج ولم يطلبه المستخدم.
- Tool أعاد بيانات رمز مختلف.
- رد ذكر رمزاً غير موجود في نتائج أدوات نفس الدور.
- رد قال لا توجد بيانات رغم وجود نتائج غير فارغة.
- رد استخدم بيانات دور سابق دون أن يسمح السؤال بذلك.

## مقاييس الحكم

لا يتم اعتبار اختيار النية صحيحاً لمجرد أن الاختبار لم يفشل. لكل سؤال تتم مقارنة:

1. هل فهم الوضعان أن السؤال سوقي أم خاص بسهم؟
2. هل تم الحفاظ على `GDWA` في سؤال السيولة فقط؟
3. هل تم تنظيف سياق `GDWA` عند سؤال الأسبوع والفرص؟
4. هل السؤال الأخير استبعد الأدوية والمخابز فعلاً من الفلاتر أو صياغة الرد؟
5. هل أدوات الوضعين أعادت بيانات مرتبطة بالرموز/القطاعات المطلوبة؟
6. هل الرد مبني على النتائج الحالية أم قال "لا توجد بيانات" رغم وجودها؟
7. هل هناك فرق زمني كبير بين استدعاء الـLLM Planner والوضع الحالي؟

يتم تسجيل النتائج كبيانات وصفية فقط، ولا يتم إعطاء درجة نجاح آلية من دون مراجعة التقرير.

## إدارة المستخدم والبيانات

- استخدام مستخدم تجريبي أو مستخدم الاختبار الموجود في آلية الاختبارات الحالية.
- استخدام جلستين مؤقتتين منفصلتين.
- حذف الجلسات/الرسائل التجريبية بعد انتهاء الاختبار إذا كان ذلك متوافقاً مع آلية الاختبارات الحالية.
- عدم طباعة مفاتيح API أو محتوى أسرار البيئة.
- عدم تضمين `environment_details` في التقرير أو الردود المحفوظة.
- الإبقاء على `automation_report.json` خارج commit لأنه ملف مولّد.

## التحقق

1. تشغيل Harness بخمس رسائل في وضع `llm_planner_first`.
2. تشغيل نفس الخمس رسائل في وضع `current_pipeline`.
3. التأكد من وجود 10 سجلات كاملة، 5 لكل وضع.
4. التأكد من تسجيل أزمنة كل رسالة، وليس زمن الجلسة فقط.
5. تشغيل `pipeline.test.js` للتأكد أن الاختبار لم يغيّر سلوك الإنتاج.
6. تشغيل الاختبار الحي الموجود فقط إذا كانت متغيرات Supabase ومفاتيح الـLLM متاحة.
7. تسليم ملخص واضح يفرق بين نتيجة الاختبار، اختلافات النية، اختلافات الأدوات، وفروق الزمن.

## خارج النطاق

- لا تعديل للـrouter الحالي.
- لا تعديل للـLLM prompts الإنتاجية.
- لا إضافة intent جديد للإنتاج.
- لا تغيير في ترتيب أو محتوى إجابات المستخدمين خارج Harness.
- لا اعتبار وضع LLM Planner الأول بديلاً إنتاجياً؛ هو baseline تجريبي للمقارنة فقط.
