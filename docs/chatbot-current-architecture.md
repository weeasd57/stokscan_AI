## 1. المخطط المعماري الكامل (Architecture Flowchart)

```mermaid
flowchart TD
    UserReq[رسالة المستخدم + التاريخ History + الصور المرفقة + ذاكرة الجلسة] --> Init[تهيئة سياق التنفيذ ونطاق المهلة Execution Scope]
    Init --> CheckVision{هل توجد صورة مرفقة؟}
    CheckVision -- نعم --> VisionProc[تحليل الرؤية واستخراج الرموز ومطابقتها مع السوق Vision Grounding]
    CheckVision -- لا --> PromptPrep[تجهيز الـ Context ونظام المحادثة]
    VisionProc --> PromptPrep
    
    PromptPrep --> ToolLoop{"حلقة الأدوات المتتابعة\n(حد أقصى: 3 جولات، 12 أداة)"}
    
    ToolLoop --> CallLLM[استدعاء DeepSeek مع مخطط الأدوات التسعة]
    CallLLM --> HasTools{هل طلب الموديل أدوات؟}
    
    HasTools -- لا / انتهت الأدوات --> DraftAns[صياغة مسودة الإجابة Draft Answer]
    
    HasTools -- نعم --> WriteCheck{هل تتضمن أداة كتابة محفظة؟}
    WriteCheck -- نعم --> AuthCheck[فحص تفويض المستخدم الصريح للكتابة Pre-Flight Authorization]
    AuthCheck -- غير مفوض --> BlockWrite[رفض عملية الكتابة وإرجاع تنبيه الأمان]
    AuthCheck -- مفوض --> ExecTool
    WriteCheck -- لا --> ExecTool[تنفيذ الأدوات المحددة بالتوازي / التسلسل agentic-tools.ts]
    
    BlockWrite --> CollectEv[تجميع الأدلة المؤرخة Agentic Evidence]
    ExecTool --> CollectEv
    CollectEv --> UpdateSyms[تحديث قائمة الرموز المستعلم عنها]
    UpdateSyms --> NextRound{هل توجد جولة تالية متاحة؟}
    NextRound -- نعم --> ToolLoop
    NextRound -- لا --> DraftAns
    
    DraftAns --> PubReview{"مراجعة ما قبل النشر Pre-Publication Review"}
    PubReview --> DetCheck[الفحص الحتمي: مطابقة أرقام الجداول مع الأدلة + حظر تسريب DSML]
    PubReview --> LLMReview[المراجع اللغوي المستقل: إتمام المهمة والسياق]
    
    DetCheck & LLMReview --> ReviewPassed{هل اجتاز الفحصين بنجاح؟}
    ReviewPassed -- نعم --> CanonicalAnswer[اعتماد الإجابة الموثقة مع الخاتمة ورابط التليجرام]
    
    ReviewPassed -- لا --> RepairCheck{هل تتوفر ميزانية للإصلاح؟\n(جولة إصلاح واحدة + وقت كافٍ)}
    RepairCheck -- نعم --> RepairTurn[إرسال أسباب الرفض للنموذج لإصلاح المسودة بدقة]
    RepairTurn --> PubReview
    
    RepairCheck -- لا --> Fallback[توليد الرد الاحتياطي الآمن safeAgenticFallback من الأدلة الخام]
    Fallback --> CanonicalAnswer
    
    CanonicalAnswer --> SSEOut[بث الإجابة المعتمدة SSE token + حفظ الجلسة ai_chat_sessions + حدث done]
```

## 3. حواجز الميزانية الصارمة (Strict Budget & Resource Governance)

لحماية الموارد ومنع الحلقات اللانهائية أو استنزاف التوكنز، يُدار كل طلب عبر ثوابت ميزانية قاطعة:

```typescript
export const AGENTIC_BUDGET = {
    toolRounds: 3,     // أقصى عدد لجولات طلب الأدوات المتتابعة
    toolCalls: 12,     // أقصى إجمالي لعدد استدعاءات الأدوات في الطلب الواحد
    repairs: 1,        // أقصى عدد لمحاولات إصلاح المسودة المرفوضة
    providerCalls: 7   // أقصى عدد لاستدعاءات واجهة DeepSeek (تخطيط + أدوات + مراجعة + إصلاح)
};
```

- **إدارة المهلة (Execution Scope & Deadline)**: يُلزم كل استدعاء لقاعدة البيانات أو واجهة LLM بمهلة إجمالية (`AI_CONFIG.limits.requestDeadlineMs`). إذا قارب الوقت على النفاد، يُلغى الاستدعاء عبر `AbortSignal` ويتم التبديل تلقائياً للرد الآمن `safeAgenticFallback`.
- **منع التكرار داخل الطلب (In-Request Deduplication)**: عند تكرار نفس أداة الكتابة داخل جولات الطلب، تُنفذ الأداة مرة واحدة فقط ويُعاد استخدام النتيجة الموثقة عبر `writeCache`.

## 4. أدوات البيانات التسعة المعتمدة (The 9 Core Tools)

تدار جميع طلبات الشات عبر 9 أدوات متخصصة يختار الموديل استدعاءها ذاتياً دون شروط كودية مسبقة:

1. `get_stock`: جلب بيانات السعر والمؤشرات الفنية (RSI, MACD, وايكوف، السيولة، نماذج KING/EGX AI).
2. `get_stock_levels`: حساب مناطق الدعم والمقاومة، نطاقات الدخول الفنية، ووقف الخسارة وجني الأرباح (TP1/TP2).
3. `manage_portfolio`: استعراض وتحديث مراكز المحفظة، تسجيل الشراء أو البيع أو الحذف بأمان كامل.
4. `get_market`: قراءة مؤشر EGX30 وحالة السوق وقوائم الأكثر ارتفاعاً وانخفاضاً مباشرة من `market_cache`.
5. `get_recommendations`: استعراض التوصيات الفنية المفتوحة أو المغلقة مع فلترة أسبوعية دقيقة وحساب الأرباح المحققة من أسعار الخروج الفعلية.
6. `get_technical_scan`: مسح فني متقدم للسوق (زخم وسيولة، اختراق MACD، تشبع بيعي RSI، الأكثر هبوطاً، إلخ).
7. `get_accumulation_stocks`: رادار التجميع المؤسسي لوايكوف وتدفق السيولة الذكية من `stock_scans_summary`.
8. `get_news`: أحدث الإفصاحات والأخبار الرسمية المفلترة بأسهم محددة أو للسوق العام.
9. `get_comparison`: مقارنة فنية ومالية مباشرة بين شركتين أو أكثر.

## 5. مراجعة ما قبل النشر وتأريض الجداول (Pre-Publication Review)

لا يتم بث أي إجابة للمستخدم إلا بعد اجتياز فحص مزدوج:

1. **الفحص الحتمي الصارم (`checkAgenticDraft`)**:
   - حظر خروج ردود فارغة أو غير مكتملة.
   - حظر تسريب وسوم الموديل الداخلية مثل `DSML` أو `<tool_call>`.
   - فحص نسبة الحقائق (`checkAttribution`) لضمان عدم اختلاق أسعار أو نسب مئوية.
   - **فحص الجداول (Table Grounding)**: فحص كافة الأرقام الواردة في جداول الماركداون (الأفقية والرأسية وتحت عناوين الأسهم) ومطابقتها مع الأدلة الفعلية لسهمها، مع استثناء ثوابت الفترات الزمنية للمؤشرات (مثل 14 في RSI أو 50 في EMA) وأرقام تسلسل الصفوف.
2. **المراجع اللغوي المستقل (Semantic LLM Reviewer)**:
   - يقرأ طلب المستخدم الأصلي، وسياق الجلسة، والنتائج المؤرخة للأدوات، ومسودة الرد.
   - يتحقق من إنجاز نفس المطلوب بدقة، وعدم ادعاء حفظ في المحفظة دون دليل، وعدم اختلاق مستويات أسعار لم ترد في الأدوات.
3. **آلية الإصلاح أو الاحتياط**:
   - في حال وجود خطأ قابل للإصلاح وتوفر ميزانية زمنية (> 6 ثوانٍ)، تُعطى فرصة إصلاح واحدة (`repaired = true`).
   - في حال استمرار الرفض أو نفاد الوقت، يُلغى نشر المسودة ويُبث الرد الاحتياطي الآمن (`safeAgenticFallback`) الذي يوضح النقص ويعرض البيانات الخام المتاحة فقط.

## 6. أمان عمليات المحفظة وقاعدة البيانات (Portfolio Safety & Concurrency)

- **فحص التفويض المسبق (Pre-Flight Authorization)**: لا تُنفذ أي عملية كتابة (`add`, `update`, `sell`, `remove`) في محفظة المستخدم بمجرد اقتراح النموذج أو ورود صورة غير مؤكدة؛ بل يُطلب تفويض مسبق يتأكد من أمر المستخدم الصريح.
- **القفل التفاؤلي (Optimistic Concurrency Locking)**: يعتمد التحديث والحذف والبيع على `lockPosition` بمطابقة `updated_at` والكميات السابقة، مما يمنع الكتابة فوق تعديلات متزامنة.
- **التدقيق المكتوب (Audit Logging)**: تسجيل كل حركة بيع أو تعديل في جدول `position_events`.
- **أثر الرصيد النقدي في البيع (`sell`)**: عملية البيع تحدّث المركز إلى `closed` أو تخصم الكمية، وترجع بوضوح `cash_updated: false` مع التنبيه الصريح بأن الرصيد النقدي لم يتغير لكونه في محفظة نقدية منفصلة.

## 8. مقاييس الاتصال والمراقبة (Telemetry & SSE Protocol)

يبث المسار أحداث Server-Sent Events (SSE) المنظمة للواجهة:
- `type: "plan"`: يوضح نية الطلب، الأدوات المستدعاة، الرموز، ورقم الجولة الحالية.
- `type: "status"`: رسائل حالة للمستخدم (فهم الطلب، قراءة الرؤية، استدعاء الأدوات، مراجعة النشر).
- `type: "tools_data"`: مصفوفة الأدلة المؤرخة كاملة للمكونات التفاعلية وجداول البيانات.
- `type: "token"`: بث الإجابة المعتمدة النهائية بعد اجتياز المراجعة.
- `type: "done"`: البيانات الختامية متضمنة:
  - تفاصيل استهلاك التوكنز (`usage: prompt_tokens, completion_tokens, total_tokens, provider_calls, tool_calls`).
  - تقرير مراجعة النشر (`publication_review: passed, final_passed, repaired, reasons, completion`).
  - تحديث الجلسة والرموز المعتمدة (`session_update`).

## 9. بروتوكول الصيانة وإجراءات الرجوع (Maintenance & Rollback Procedure)

في حال حدوث أي طارئ غير متوقع في بيئة الإنتاج:

1. **التحقق من السيرفرات والأدوات محلياً**:
   - فحص الاختبارات غير الحية: `npm run test:offline` (يجب أن تنجح كافة الاختبارات 100%).
   - فحص أنواع TypeScript: `npx tsc --noEmit` (0 أخطاء).
   - التأكد من صحة سيرفرات التطوير (FastAPI على 8000 و Next.js على 3000).
2. **قواعد منع هدر سجلات Supabase**:
   - **يُمنع منعاً باتاً** استخدام أدوات `query_logs` أو الاستعلام عن سجلات Supabase البعيدة في المراجعات الدورية أو المراقبة.
   - التحقق يتم دائماً عبر الجداول المباشرة ذات الصلة (`daily_job_runs`, `positions`) مع `.limit(1)` وإسقاطات أعمدة محددة.
3. **طريقة الرجوع (Rollback Procedure)**:
   - في حال الرغبة في الرجوع السريع لأي سبب، يتم الرجوع إلى النقطة المحفوظة `64f3036f` في Git عبر:
     ```bash
     git revert --no-commit HEAD
     ```
   - المعمارية الحالية تغطي كافة وظائف الإصدارات السابقة وتضيف عليها الأمان والموثوقية، لذا يُوصى دائماً بتعديل المشكلة في الملف المعياري المختص (`agentic-runtime.ts` أو `agentic-tools.ts` أو `agentic-publication.ts`) بدلاً من الرجوع.
